# Native ASH xTB point-charge I/O benchmark

This benchmark compares ASH's built-in `xTBTheory` point-charge writer and
`pcgrad` reader with the NumPy fast-I/O functions used by `ash_pes2d`. The fast
functions are enabled as a runtime monkeypatch for the comparison. No ASH or
xTB source code was changed.

It covers every QM/MM system shipped in the ASH examples and tests whose inputs
are present or can be generated by the example's own preparation scripts
(12 gradient cases plus one energy-only case). See *Example coverage* for the
three examples that cannot be run and why.

## Setup

- ASH checkout: branch `master` at `c4712777`.
- xTB: 6.8.0.
- xTB and OpenMM use one CPU thread.
- **E + gradient** rows call `QMMMTheory.run(Grad=True)`: one full QM/MM energy
  and gradient. **MD force** rows are the MD examples, which keep rigid water
  and H-bond constraints; `OpenMMTheory.run()` refuses constrained systems, so
  these call the QM/MM object the way ASH's `OpenMM_MD` does (QM energy plus the
  QM and point-charge gradient; OpenMM integrates the MM forces itself).
- Each row's full-call time is one call in native mode and one in fast-I/O
  mode. These single timings are sensitive to OpenMM and CPU scheduling.
- Writer and reader times are medians over 25 repetitions using the exact
  point-charge arrays and `pcgrad` file produced by the native ASH run.
- Exactness checks compare energies, full gradients, PC gradients, and the
  numeric records read back from both `pcharge` files.

## Results

All twelve gradient cases, and the energy-only phenol case, give **exactly
equal** energies, gradients, point-charge gradients and point-charge records in
native and fast-I/O mode. Every difference in Tables 7–9 is zero.

Reading the tables:

- Times in Tables 3–5 are medians over 25 repetitions of the isolated file
  routine. Speedup is native time divided by fast time, so values below 1×
  mean fast I/O is slower.
- Full-call times (Table 5) and in-run I/O times (Table 6) are single
  measurements, one per mode, so the full-call speedup mostly reflects
  run-to-run noise rather than the I/O change.
- For **E + gradient** cases the energy is the total QM/MM energy and the
  gradient covers all atoms. For **MD force** cases the energy is the QM energy
  minus ASH's external-force correction term and the gradient is the QM plus
  point-charge gradient, as returned to `OpenMM_MD`.
- The Na₂HPO₄ energy is positive because the example's UFF Lennard-Jones term
  on the unrelaxed 502-atom cluster is +2469 Eh; the QM energy is −24.445 Eh.

## Findings

The `pcgrad` reader is about 3× faster in every case above a few hundred point
charges (Table 4), with tight minimum-to-maximum spreads.

The writer is about 1.1× faster for ten of the twelve systems (Table 3). For
DHFR and 3FGABA the fast writer's median is slower (0.75× and 0.81×), but its
timings there are widely scattered: 74–150 ms for DHFR, against 79–86 ms
native. Inside the full calls the two writers took the same time for DHFR
(Table 6). The fast writer is therefore not reliably faster for these two
systems; whether it is genuinely slower was not established.

Combined file I/O is about 1.35× faster where the writer behaves, saving
9–15 ms per call for the proteins (about 0.3% of a 3.4–5.5 s call) and about
1.5 ms for the small water boxes (4–5% of a 32–36 ms MD force call). Native
file I/O is about 1% of a protein QM/MM call but 16–40% of an MD force call,
where OpenMM's MM work is not part of the timed call (Table 5).

## Adaptations

Every departure from an example script is listed here and in the `adaptation`
field of [results.json](results.json).

- **QM program.** Examples written for ORCA or PySCF are run with xTB in its
  place (GFN1 for rubredoxin, as in that example's own xTB scripts; GFN2
  elsewhere). QM regions, charges, multiplicities and MM setup are unchanged.
- **TIP3P file.** The solvation examples load `amber/tip3p_standard.xml`, which
  comes from `openmmforcefields` and is not installed. They are run with the
  water file ASH's own `solvate_small_molecule` selects for the same ligand
  XML: `amber14/tip3p.xml` for the Amber-scaled ligand files, and ASH's
  `databases/forcefields/tip3p_water_ions.xml` for the 3FGABA `LIG.xml`
  (1–4 scaling 1.0).
- **Generated inputs.** `prepare_inputs.sh` runs the examples' `solvate.py` and
  `run_mm_md.py` (isobutyraldehyde, FeCl₄⁻) and the Molcrys step of
  `molcrys-test.py` (Na₂HPO₄, ORCA BP86 as written). The outputs used here are
  stored in `prepared/`. ASH's automatic re-imaging fails for the bond-less
  FeCl₄⁻ solute, so that frame is re-imaged with `image_on_solute.py`.
- **FeCl₄⁻ charge and multiplicity.** `run_qmmm_md.py` passes `qm_charge=0,
  qm_mult=1`, while `solvate.py`, `create_ff.py` and the ligand charges
  (sum −1) describe the −1 sextet. The benchmark uses −1 / 6.
- **Rubredoxin QM-I** passes `unusualboundary=True`, as its example does.
  QM-III is the example's deliberately invalid region and is not run.
- **Na₂HPO₄** uses `codeversion="py"` for the Lennard-Jones arrays because the
  default Julia routine needs `juliacall`, which is not installed.

| BF₃·HCN Molcrys xTB test (`17a`) | Not runnable | Reads a CIF from an author-local path; the file is not in the checkout. |
| DHFR Amber/CHARMM MD (`OpenMM-other-setups`), ferredoxin preparation | Out of scope | MM-only or preparation-only; no QM region is defined. |

Gas-phase xTB examples (butane metadynamics, umbrella sampling, optimizer and
NEB tests) do not use point-charge embedding and never call these file routines.

## Reproduce

Use a Python environment with ASH's dependencies (OpenMM, NumPy, MDTraj), with
`xtb` on `PATH`. Run from the ASH checkout; `ASH_PES2D` is the directory that
contains the `ash_pes2d` package.

```bash
PYTHONPATH="$PWD:$ASH_PES2D" python benchmarks/native_xtb_pc_io/run_benchmark.py \
  --workdir /tmp/ash-native-io-benchmark/reproduced --repetitions 25
```

`--cases` selects a subset and `--xtb-dir` points at a specific xTB build. The
runner writes `results.json`, `results.csv` and per-call arrays into the work
directory. Copy the two result files into this folder and run `make_tables.py`
to rebuild the README tables.

Run the legacy energy-only case separately with:

```bash
PYTHONPATH="$PWD:$ASH_PES2D" python benchmarks/native_xtb_pc_io/run_phenol_energy_only.py
```

To regenerate `prepared/` (needs ORCA on `PATH` or `ORCA_DIR` set, and the
OpenBabel Python module; the MM equilibrations are stochastic, so the boxes
will differ in detail):

```bash
PYTHON=python benchmarks/native_xtb_pc_io/prepare_inputs.sh /tmp/ash-native-io-benchmark/prepare
```

Stored benchmark data in this folder is in [results.json](results.json)
and [results.csv](results.csv); the example inventory is also available as
[coverage.csv](coverage.csv).
